# Suli Pool Admin — Context & Known Bugs

This is the Quasar (Vue 3 + Pinia) admin panel for sulipool.com, pulled fresh from GitHub on 2026-09-07. It talks directly to the same Supabase project as `suli-pool-front` (`uezqjtmlllvtxygxhkzh`), using the browser-authenticated `anon` client (Supabase Auth login, not a service-role backend). Two real admin logins exist (`info@sulipool.com`, `adminsuli@gmail.com`); a throwaway `claude-agent-test@sulipool.com` account was created for QA during this session and can be deleted later (Supabase → Auth → Users).

## How this codebase is shaped

- 11 CRUD sections, one per sidebar item in `MainLayout.vue`: Hero, Installation, Why We Different, Company Stats, About, Projects, Locations, Timeline, Social Media, Site Sections, Company & Team. Each is a `pages/*Page.vue` + `stores/*-store.ts` pair.
- Every content-with-translations table follows the same shape: a base row (`is_enabled`/`sort_order`), a `*_translations` table (one row per locale: `en`/`ar`/`ckb`), and sometimes a `*_images` join table → `media_assets` (`{bucket, path, alt}`).
- Image uploads go through `composables/useImageCompression.ts` (browser-side compression) then `supabase.storage.from('site-images').upload(...)`, consistently, everywhere.
- Auth: `stores/auth-store.ts` + a `router/index.ts` navigation guard redirect anyone unauthenticated to `/login`.

## The confirmed root-cause bug: image/photo uploads were completely broken

Live-tested 2026-09-07 by logging in and trying to upload a team member photo: creating a `team_members` row with no photo succeeds; attaching a photo fails every time with `new row violates row-level security policy`, thrown from the `storage.objects` insert inside `supabase.storage.from('site-images').upload()`.

**Root cause:** the `site-images` bucket exists and is public-read, but `storage.objects` has no RLS policy allowing the `authenticated` role to INSERT/UPDATE/DELETE. The repo already has a pattern for this (`enable_hero_rls_policies.sql`, `enable_company_team_rls_policies.sql`, etc. — one file per table, meant to be run by hand in the Supabase SQL Editor) but **no one ever wrote or ran the storage-bucket equivalent**. This affects every single image upload feature in the whole admin, not just team photos — Hero slides, About images, Installation/Timeline/Project/Site-section images all use the same bucket and the same client-side write path.

Fix: `enable_storage_rls_policies.sql` (new, at repo root) — **must be run in Supabase → SQL Editor** by the client/owner; it isn't something that can be applied through the anon/service REST API. This one script unblocks every image feature at once.

**Why this matters for the "team avatars" ask:** the front-end (`suli-pool-front`) already has real `team_members` rows (6 people) and already renders them with `TeamMemberCard.vue`, falling back to a placeholder icon when `image_url` is null — which it is for all 6, today. The admin's Company & Team page already has full add/edit/delete/upload UI for this (it was not missing functionality) — it was just silently failing on the one write that matters. `suli-pool-front` also has a separate, deliberately hacky, token-gated `/admin/team` upload page (`app/pages/admin/team.vue` + `server/api/admin/team-photo.post.ts`) that uploads to a *different* bucket (`team-photos`) via the service-role key — built as a stopgap before this admin panel existed. Once the storage policy fix lands and is verified, that stopgap page/route in the front-end repo is redundant and should be considered for removal (not done here — out of scope for the admin repo, flagged for later).

## Other confirmed bugs (found via live schema introspection + a full source audit)

Schema ground-truth was pulled directly from the live PostgREST OpenAPI spec (not from the stale docs below), and one write was live-tested against `about_section_translations` to confirm NOT NULL constraints.

1. **Timeline event creation is completely broken.** `timeline_items.section_key` is `NOT NULL` in the real DB, but neither `TimelinePage.vue`'s form nor `timeline-store.ts`'s `createEvent` ever sets it. Every "Add Event" submission fails. (`create_installation_timeline_tables.sql` at repo root describes an entirely different, stale schema — `installation_steps`/`timeline_events`/`event_date` — don't trust it.)
2. **About Section translations landmine.** Every text column on `about_section_translations` (`eyebrow_text`, `section_title`, `card_title`, etc.) is `NOT NULL` — confirmed by a live test insert. `AboutSectionPage.vue`'s `openEditDialog()` fills any locale missing a translation row with `null` fields, and `about-store.ts` inserts them as `null`. Dormant today (all 3 locales already have rows) but will throw an unhandled-looking Postgres error the moment that's not true.
3. **Orphaned `media_assets` rows / unsafe cross-table deletes.** `about-store.ts`'s `deleteAboutImage` is the one store that correctly checks whether a `media_assets` row is still referenced elsewhere before deleting it. `hero-store.ts` (`deleteHeroSlideImage`, and `deleteHeroSlide` doesn't clean up `media_assets` at all) and `site-section-store.ts` (`deleteSiteSectionImage`) skip that check — deleting a shared/reused image asset out from under another section, or leaking rows forever on every Hero slide deletion.
4. **`table-resolver.ts`** — a runtime schema-probing helper used by `installation-store.ts`, `timeline-store.ts`, and `locations-store.ts` to guess real table names via extra `select().limit(1)` round-trips, with a module-level cache that can pin a bad guess for the rest of a session. The real schema is confirmed and stable (`installations`, `location` singular, `timeline_items`) — this whole file is unneeded indirection/latency now.
5. **Dead/unreachable code:** `IndexPage.vue`, `ExampleComponent.vue`, `models.ts`, `example-store.ts`, `EssentialLink.vue`, `hero-schema-helper.ts`, `stores/types/database.types.ts` (stale — still says `locations` plural) are all unreferenced Quasar scaffold leftovers. `DashboardPage.vue` is routed at `/features` but that route isn't linked from the sidebar — unreachable.
6. **UX gaps vs. the established pattern** (About/Company&Team are the most complete pages): `CompanyStatisticsPage.vue` has no client-side required-field validation despite `label_en`/`value` being `NOT NULL` (raw Postgres error surfaces instead); the About/Team-members error banner is sticky pinia state — a failed create/update/delete left `store.error` set, which blanks out the already-loaded list behind an error banner until the next successful fetch, even though the cached list data was still fine (live-confirmed: canceling a dialog after a failed photo upload hid the whole Team Members list); Social Media links open with `target="_blank"` and no `rel="noopener noreferrer"`; Login page has decorative "Remember me"/"Forgot password" controls with no wiring.
7. **~5,000 lines of duplicated CSS** across `css/sections/*.scss` and inline page `<style>` blocks — the same badge/status/image-grid/responsive-dialog patterns copy-pasted across 8–10 files. The main lever for a "clean/lean" pass, but a large, lower-risk-to-defer refactor — tracked in `todo.md`, not done wholesale in this pass.
